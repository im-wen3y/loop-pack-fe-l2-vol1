LOOP PACK · WEEK 10

E2E 조건부 실행 수정 방향

PR에서 바뀐 경로를 먼저 분류하고, 실제로 영향을 받을 가능성이 있는 E2E만 선택한다. 다만 판단할 수 없는 변경이나 판별 실패는 생략하지 않고 전체 E2E로 보낸다.

현재 상태 · 문서-only E2E 생략 검증 완료, 선택 실행 검증 대기

변경 감지 job과 조건부 테스트 선택을 workflow에 반영했고, 필수 결제·주문 조합과 인증 조합을 로컬 Chromium·WebKit에서 통과시켰다. 실제 PR의 경로 분류·step 생략·required check 상태를 확인했으며, PR #13에서 문서-only 변경의 E2E 준비·실행 step 생략도 확인했다. 다음으로 로직 변경의 선택 spec 실행과 알 수 없는 변경의 전체 실행 fallback을 검증한다.

01 · 결정 요약

Quality는 유지하고 E2E만 조건부로 조정한다

실행

JS/TS 로직 변경이면 Chromium과 WebKit에서 order.spec.ts를 항상 실행한다.

추가 실행

변경된 기능의 spec을 결제·주문 테스트에 더한다.

생략

문서-only와 CSS-only 변경에서는 E2E의 설치·build·테스트를 생략한다.

안전 기본값

분류할 수 없거나 판별에 실패하면 전체 E2E를 실행한다.

Quality의 문서·스타일 조건부 분리는 별도 판단으로 보류했다. 이 문서는 E2E의 실행 범위와 required check 표시 문제만 다룬다.

02 · 판별 신호

변경 감지 job이 다음 값을 만든다

paths-filter로 PR의 변경 경로를 읽고, 뒤의 E2E matrix job이 사용할 boolean 신호를 만든다. 신호는 파일 내용을 해석하는 값이 아니라 경로 규칙의 결과다.

changes job의 출력값
값 true가 되는 경우
run_e2e 문서·CSS-only가 아니거나, 분류 실패·미지의 경로가 있는 경우
all 공통 로직, fixture, 설정, lockfile, workflow, 미지의 변경 또는 판별 실패
auth · cart · wishlist · product 각 기능의 소스 또는 대응 spec이 변경된 경우
오타는 경로만으로 판별하지 않는다

.tsx 안의 문구 오타와 동작 로직 변경을 CI가 안전하게 구분할 수 없다. 따라서 JS/TS 파일 변경은 로직 변경 가능성이 있는 것으로 보고 E2E를 실행한다.

03 · 변경 범위 매핑

필수 결제 테스트에 영향 범위를 더한다

현재 정한 E2E 선택 규칙
변경 경로 실행할 spec 판정 이유
인증 로직 또는 auth.spec.ts order.spec.ts + auth.spec.ts + logout.spec.ts 결제 필수 흐름과 인증 회귀를 함께 확인
장바구니 로직 또는 add-to-cart.spec.ts order.spec.ts + add-to-cart.spec.ts 장바구니에서 주문으로 이어지는 흐름 확인
위시리스트 로직 또는 add-to-wishlist.spec.ts order.spec.ts + add-to-wishlist.spec.ts 변경된 위시리스트 동작과 결제 필수 흐름 확인
상품 목록·검색·필터·정렬 로직 order.spec.ts + state-restoration.spec.ts 상품 상태와 URL·스토리지 복원 회귀 확인
공통 로직, fixture, 설정, lockfile, workflow 전체 E2E 영향 범위를 특정하기 어려움
문서-only 또는 CSS-only 생략 브라우저 동작 로직이 바뀌지 않음
분류 불가 또는 판별 실패 전체 E2E 검증 누락보다 실행 비용을 선택하는 안전 기본값

04 · 실행 흐름

matrix는 유지하고 테스트 선택만 바꾼다

PR
  └─ changes
       ├─ 변경 경로 분류
       ├─ run_e2e / all / 기능별 신호 출력
       └─ 판별 실패 → all=true

  └─ E2E matrix (chromium, webkit)
       ├─ 문서·CSS-only → 설치·build·테스트 step 생략
       ├─ 기능 변경 → order.spec.ts + 영향 기능 spec
       └─ all=true → 전체 Playwright 테스트

브라우저별 독립 required check는 유지한다. 따라서 두 브라우저가 각각 같은 선택 규칙을 적용하고, 한 브라우저에서만 실패해도 어느 엔진에서 문제가 났는지 확인할 수 있다.

05 · required와 생략

workflow는 시작하고, matrix job은 화면에 남긴다

workflow-level 경로 제외는 사용하지 않는다

paths-ignore로 workflow 자체를 생략하면 required check가 생성되지 않아 PR이 대기할 수 있다. 변경 감지 job은 항상 실행하고, E2E matrix 안에서 실행 step을 조건부로 생략한다.

문서·CSS-only PR에서 기대하는 화면
check 표시 의미
changes Success 변경 범위를 판별함
E2E (chromium) Success job은 생성됐지만 무거운 step은 Skipped
E2E (webkit) Success job은 생성됐지만 무거운 step은 Skipped

`develop`의 `merge-required-ci` ruleset과 네 required check는 PR #12에서 확인했다. 문서-only PR에서도 job 자체는 생성되고 무거운 step만 생략되는 것을 PR #13에서 확인했다. 판별 실패를 성공으로 처리하는 우회 경로는 만들지 않는다.

06 · 구현 순서

작은 변경부터 차례로 적용한다

  1. changes job을 추가하고 paths-filter를 커밋 SHA로 고정한다.
  2. 기능·spec·fixture·설정 경로를 필터로 선언하고 outputs를 만든다.
  3. E2E matrix job에 needs: changes를 연결한다.
  4. all이면 전체 테스트, 아니면 필수 order와 영향 spec을 선택한다.
  5. 문서·CSS-only에서는 install, browser install, build, test step을 생략한다.
  6. 알 수 없는 변경과 판별 실패의 fallback을 전체 E2E로 연결한다.
  7. 구현 결과와 실제 PR 로그를 RFC에 기록한다.
다음 검증 항목

e2e.yml에 changes job과 조건부 테스트 선택을 추가했다. 로직·fixture·설정 변경이 포함된 PR의 전체 실행과 develop required ruleset, 문서-only PR의 E2E 생략을 확인했다. 다음 PR에서는 기능 로직 변경 시 필수 order와 영향받은 spec만 선택되는지 확인하고, 알 수 없는 경로는 전체 E2E로 fallback되는지 확인한다.

업데이트 계획 · 문서-only 검증 브랜치

develop 머지가 어려운 경우, 현재 workflow가 반영된 feat/week-10에서 feat/week-10-docs-only를 새로 만든다. 새 브랜치에서는 docs/week-10/ 아래 문서만 작게 수정하고, PR의 base를 feat/week-10으로 지정해 diff를 문서-only로 만든다.

  • Detect E2E scope: run_e2e=false
  • Chromium·WebKit job은 생성되고 install·browser install·build·test는 Skipped
  • Quality는 기존대로 실행

이 PR의 base가 develop이 아니므로 네 check가 Required로 표시되지 않을 수 있다. 생략 동작은 이 PR에서 검증하고, required 표시는 develop 대상 PR #12 증거를 사용한다.

07 · 검증 계획

로컬 조합은 통과했고, PR에서 생략과 실행을 증명한다

검증 PR 확인할 내용

fixture·설정·공통 로직 all=true, tests=all 두 브라우저에서 전체 E2E 실행
분류할 수 없는 경로 또는 감지 실패 E2E fallback 또는 all=true 생략하지 않고 전체 E2E 실행

회차마다 남길 값

  • PR URL과 기준 커밋 SHA
  • Detect E2E scope의 filter 결과와 run_e2e·all 값
  • Chromium/WebKit job URL과 전체 job 시간
  • 각 job의 실제 실행 또는 Skipped step, 선택된 spec 목록
  • required check가 성공·실패·대기로 표시됐는지

# 10주 기술 회고

## 1. 프로젝트 요약

이 프로젝트는 Next.js 16 App Router와 React 19 기반의 커머스 애플리케이션입니다. 이번 주에는 기능을
늘리기보다 어떤 변경이 어떤 검증을 통과해 배포되는지 설명할 수 있도록 CI 조건, 예산 게이트와 AI
리뷰 기준을 정리했습니다.

## 2. 10주 동안의 구조 변화

2~3주차에는 컴포넌트와 훅의 책임을 나누고, 6주차에는 FSD 레이어·슬라이스와 Public API 경계를
정리했습니다. 8주차에는 단위·통합 테스트와 브라우저 경계를 구분했고, 9주차에는 인증·라우팅·브라우저
흐름을 Playwright E2E로 남겼습니다. 10주차에는 이 경계를 CI 실행 조건과 결정적 소비처 검사로 연결했습니다.

## 3. 주요 기술 결정 3개와 근거

### 조건부 E2E 경로 분류와 미분류 fallback

처음에는 변경 경로를 path filter로 나누면 E2E 비용을 간단히 줄일 수 있다고 생각했습니다. 그러나
route가 추가될 때마다 분류 목록과 예외 처리를 갱신해야 했고, 미분류 경로가 검증에서 빠질 위험도
있었습니다. 그래서 명확히 스킵할 수 있는 문서·스타일 변경만 제외하고, 미분류 변경은 전체 E2E로
승격했습니다. 실제 scope 결과는 [PR #12](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/12)의
전체 실행과 [PR #13](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/13)의 문서-only 스킵에서
확인했습니다.

### 환경 변수 차단 게이트와 번들 advisory

환경 변수 오류는 잘못된 API 주소나 secret 노출처럼 배포 전에 막아야 할 설정 사고이므로 required
경로에서 실패하게 했습니다. 번들 예산은 7주차 측정값 `273.74 kB`에 5% 여유폭을 더한 `287.4 kB`를
기준으로 삼았지만, 되돌리기 쉬운 성능 저하라는 판단에 따라 advisory로 두고 초과량을 PR 코멘트에
노출했습니다. 실제 환경 변수 오류는 [PR #20](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/20)에서
Quality failure로 확인했고, 번들 초과는 [PR #21](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/21)에서
경고·리포트로 확인했습니다.

### 캐시 추가 최적화 보류

pnpm 캐시 hit·miss 시간을 비교한 결과 hit install은 약 2초, miss는 약 6~7초였습니다. 설치가 전체
CI의 가장 큰 병목은 아니었으므로 캐시 키를 더 복잡하게 나누는 최적화는 보류했습니다. 대신 matrix
job이 같은 키를 공유하면 일부 job이 먼저 저장한 캐시를 복원할 수 있다는 실험 한계를 기록했습니다.
상세 raw 값과 로그는 [`week10-ci.md`](./week10-ci.md#캐시)에 남겼습니다.

## 4. 테스트와 품질 게이트

Quality는 test·lint·typecheck·build를 모든 PR에서 실행합니다. E2E는 변경 범위에 따라 필요한 스펙을
실행하고, 감지 실패나 미분류 경로는 전체 실행으로 fallback합니다. 최종 PR #12에서는 Detect E2E
scope, Chromium, WebKit, Quality와 Vercel 검사가 모두 통과했습니다.

로컬 `pnpm verify`는 테스트 29개 파일·164개 테스트, lint, typecheck를 통과했습니다. Public API
검사는 `pnpm lint` 안에서 실행되며, `pnpm check:public-api`로 단독 재현할 수 있습니다.

## 5. 성능 측정 결과

Before 측정에서 E2E의 가장 긴 구간은 `Run E2E tests`였고 중앙값은 약 57초였습니다. 브라우저 설치는
약 46–52초였으며, pnpm 캐시 hit·miss에 따른 install 차이는 약 2초 대 6–7초였습니다. 따라서 설치
캐시를 더 복잡하게 만드는 것보다 브라우저별 job을 독립 실행하고 필요한 경로만 E2E에 태우는 조건
설계에 집중했습니다. 측정의 상세 raw 값·범위·한계는 [`week10-ci.md`](./week10-ci.md#before)에
있습니다.

## 6. CI/CD와 AI 협업

Quality와 E2E workflow에는 최소 권한과 action SHA 고정을 적용했고, PR 코멘트가 필요한 Quality job에만
`pull-requests: write`를 부여했습니다. AI는 workflow·스크립트 골격과 PR 지적 후보를 제시했지만,
required 배치·예산·E2E 조건·승격 룰은 작성자가 로그와 실제 diff를 대조해 결정했습니다.

PR #12 AI 리뷰에서는 P2 네 건과 P4 한 건을 실제 라인 코멘트로 전달했습니다. `APP_ORIGIN` 검증
지적은 채택해 수정했고, pagination 의견은 유효하지만 이번 범위의 P4로 기각했습니다. 코드 사실과
규칙에 반하는 실제 오탐은 확인하지 못했으므로 오탐을 만들어 기록하지 않았습니다.

## 7. AI·사람·기계의 역할

기계는 test·lint·typecheck·build·환경 변수 형식·Public API 소비처처럼 참과 거짓을 결정적으로 가를
수 있는 항목을 맡습니다. AI와 사람은 설계 냄새, 실행 조건의 적절성, 예산의 우선순위와 같은 맥락
판단을 맡고, AI의 제안은 실제 diff·로그·실험으로 확인한 뒤에만 채택합니다. 이번 주 Public API
소비처 검사는 반복 지적을 기계 게이트로 내린 사례이며, 어떤 심볼을 공개할지는 여전히 사람이
결정하도록 경계를 남겼습니다.

## 8. 다시 만든다면

처음부터 path filter의 분류 목록과 미분류 fallback을 함께 설계하겠습니다. 캐시도 설정을 추가하기
전에 hit·miss 시간을 먼저 측정하고, 병목이 확인된 경우에만 키나 job 구조를 바꾸겠습니다. AI 리뷰는
초기 프롬프트에 파일·라인 근거와 추측 금지 조건을 명시하고, 오탐이 실제로 확인된 경우에만 전후
프롬프트를 비교하겠습니다.

## 제출 질문

### 1. E2E를 모든 PR에 required로 걸면 어떤 문제가 생길까?

E2E 테스트가 불필요한 문서-only PR에서도 실행되면 실행 시간과 CI 비용이 늘어나 업무 병목이 생길 수
있습니다. 또한 E2E를 required로 두면서 조건부로 실행하면, 스킵된 PR의 check가 영구 대기 상태가 될
수 있습니다. 그래서 저비용 검증은 모든 PR에서 실행하고, E2E는 관련 경로에서만 실행하되 스킵 시에도
성공으로 정리되는 guard 구조가 필요합니다.

### 2. Lighthouse 점수 하락은 항상 merge blocker여야 할까?

Lighthouse 점수가 하락했다고 해서 항상 merge blocker로 둘 필요는 없다고 생각합니다. 크래시나 핵심
사용자 흐름 중단처럼 즉시 동작을 깨뜨린 문제가 아니라면, 측정 변동성과 영향 범위를 확인한 뒤 PR
머지 후 후속 개선으로 다룰 수 있습니다. 다만 반복적인 하락이나 사전에 정한 임계값을 크게 넘은
경우에는 별도 판단을 통해 차단할 수 있습니다.

### 3. Preview 환경이 production API를 바라보면 무슨 일이 생길까?

Production API와 운영 DB에는 실제 운영 데이터와 깨끗한 상태가 유지되어야 합니다. Preview가
Production API를 바라보면 Preview에서 수행한 로그인·주문·테스트 요청이 운영 DB에 기록될 수 있어
데이터 오염과 사용자 영향으로 이어집니다. 따라서 Preview에서는 배포별 URL이나 별도 테스트 환경을
사용하고, `APP_ORIGIN`이 다른 환경을 가리키지 않는지 build 전에 검증해야 합니다.

### 4. AI가 만든 workflow를 그대로 머지하면 어떤 리스크가 있을까?

AI가 만든 workflow는 조건문 오류로 필요한 검증을 스킵하거나, 실패 상황을 통과시키고, 권한 또는
secret 키를 과도하게 노출할 수 있습니다. 따라서 조건문이 정상 동작하는지 실패 상황을 만들어 확인하고,
실제 PR에서도 실행해 봐야 합니다. 또한 workflow 권한이 최소인지와 secret 값이 로그·step 환경 변수에
노출되지 않는지를 반드시 확인해야 합니다.
